# checkbox-mcp

[MCP](https://modelcontextprotocol.io)-сервер для API сервісу [Checkbox](https://checkbox.ua) — програмного реєстратора розрахункових операцій (ПРРО). Із ним ШІ-асистент, наприклад Claude, відповідає на запитання про чеки, зміни, X- та Z-звіти, товари й замовлення вашої організації. А якщо ви прямо це дозволите — відкриває й закриває зміни та створює фіскальні чеки.

English: [README.md](README.md)

> **Неофіційний проєкт.** Він не пов’язаний із Checkbox і не схвалений цією компанією. «Checkbox» — торговельна марка її власника. Ви користуєтеся сервером на власний ризик: чеки, створені інструментами запису, — справжні фіскальні документи.

> **Стан: версія 0.1.0, на справжній касі ще не перевірено.** Сервер написано за офіційним [описом OpenAPI](https://api.checkbox.ua/api/openapi.json) (версія 2.108.3) та публічною [вікі Checkbox](https://wiki.checkbox.ua/uk/api). Усі тести працюють з імітацією HTTP і звіряють кожен запит зі знімком цього опису OpenAPI. Зі справжнім API Checkbox сервер ще ніхто не запускав — ні з тестовим касиром, ні з бойовим. Докладніше — у розділі [Обмеження](#обмеження).

## Що таке ПРРО і Checkbox

В Україні продавець має реєструвати кожен продаж кінцевому покупцеві в Державній податковій службі (ДПС). Пристрій або програма, що це робить, називається реєстратором розрахункових операцій (РРО). **ПРРО** — його програмний різновид: замість сертифікованого касового апарата програма підписує кожен чек електронним підписом касира, передає його до ДПС і отримує фіскальний номер. Робота поділена на **зміни**: касир відкриває зміну, видає чеки й закриває зміну **Z-звітом** — денним підсумком, який надходить до податкової. **Checkbox** — один із таких сервісів ПРРО; він має вебкабінет, мобільні застосунки та REST API, з яким і працює цей сервер.

## Швидкий старт

Потрібні Node.js 20 або новіший і облікові дані касира Checkbox. Щоб спробувати сервер, візьміть **тестового касира й тестову касу**, які Checkbox створює для кожного облікового запису (див. [Як спробувати на тестових даних Checkbox](#як-спробувати-на-тестових-даних-checkbox)).

### Claude Desktop

Додайте сервер до файлу `claude_desktop_config.json` (Settings → Developer → Edit Config):

```json
{
  "mcpServers": {
    "checkbox": {
      "command": "npx",
      "args": ["-y", "@myradostudio/checkbox-mcp"],
      "env": {
        "CHECKBOX_PIN_CODE": "пін-код касира",
        "CHECKBOX_LICENSE_KEY": "ключ ліцензії каси"
      }
    }
  }
}
```

Якщо у Windows сервер не запускається, вкажіть `"command": "cmd"` і `"args": ["/c", "npx", "-y", "@myradostudio/checkbox-mcp"]`.

### Claude Code

```bash
claude mcp add --transport stdio \
  --env CHECKBOX_PIN_CODE=ваш-пін-код \
  --env CHECKBOX_LICENSE_KEY=ваш-ключ-ліцензії \
  checkbox -- npx -y @myradostudio/checkbox-mcp
```

### Cursor

Додайте такий самий блок до `~/.cursor/mcp.json` (для всіх проєктів) або `.cursor/mcp.json` (для одного проєкту):

```json
{
  "mcpServers": {
    "checkbox": {
      "command": "npx",
      "args": ["-y", "@myradostudio/checkbox-mcp"],
      "env": {
        "CHECKBOX_PIN_CODE": "пін-код касира",
        "CHECKBOX_LICENSE_KEY": "ключ ліцензії каси"
      }
    }
  }
}
```

Так само сервер підключається до будь-якого іншого MCP-клієнта, що вміє запускати локальний stdio-сервер: команда `npx -y @myradostudio/checkbox-mcp` і змінні середовища з таблиці нижче.

Після цього можна питати, наприклад:

- «Під яким касиром ти працюєш і чи відкрита зміна?»
- «Покажи вчорашні чеки й суму за кожною формою оплати».
- «Знайди Z-звіти за минулий тиждень і виведи останній».
- «Каса зараз онлайн? Скільки залишилося офлайн-кодів?»

## Налаштування

Сервер налаштовується лише змінними середовища. Під час запуску він їх перевіряє і, якщо чогось бракує, завершує роботу з поясненням у stderr.

| Змінна | Обов’язкова | Типове значення | Призначення |
| --- | --- | --- | --- |
| `CHECKBOX_PIN_CODE` | один зі способів входу | | Пін-код касира. Спосіб входу, який рекомендує Checkbox. Потребує `CHECKBOX_LICENSE_KEY`. |
| `CHECKBOX_LOGIN` | один зі способів входу | | Логін касира. Використовується разом із `CHECKBOX_PASSWORD`, якщо пін-код не задано. |
| `CHECKBOX_PASSWORD` | разом із логіном | | Пароль касира. |
| `CHECKBOX_LICENSE_KEY` | див. призначення | | Ключ ліцензії каси. Потрібен для входу за пін-кодом, для режиму запису та для інструментів, що звітують про «цю» касу (`get_cash_register` без ідентифікатора, `get_offline_status`, `get_periodical_report`, `list_shifts` із `scope: "cash_register"`). |
| `CHECKBOX_API_URL` | ні | `https://api.checkbox.ua` | Адреса API. Лише `https://` (звичайний `http://` дозволено тільки для localhost). |
| `CHECKBOX_ALLOW_WRITE` | ні | вимкнено | Значення `1` вмикає інструменти запису. Якщо значення не належить до `1`/`true`/`yes`/`on` чи `0`/`false`/`no`/`off`, сервер не запуститься. |

Пін-код і ключ ліцензії можна знайти в особистому кабінеті Checkbox, у розділах із касирами та касами. Якщо задано і пін-код, і пару «логін — пароль», сервер входить за пін-кодом.

## Інструменти

Суми — цілі числа в **копійках** (13550 означає 135,50 грн), кількість — цілі числа в **тисячних** (1000 — це 1 шт., 2250 — це 2,25 кг), так само як в API Checkbox. Сервер повідомляє про це моделі.

### Інструменти читання (доступні завжди)

| Інструмент | Що повертає | Запит до API |
| --- | --- | --- |
| `get_cashier_profile` | Касира, під яким виконано вхід, його права, ознаку тестового касира та організацію | `GET /api/v1/cashier/me` |
| `list_cash_registers` | Каси з фіскальним номером, адресою, режимом (онлайн чи офлайн) і відкритою зміною | `GET /api/v1/cash-registers` |
| `get_cash_register` | Одну касу за ідентифікатором або ту, якій належить ключ ліцензії | `GET /api/v1/cash-registers/{id}` або `GET /api/v1/cash-registers/info` |
| `get_offline_status` | Кількість доступних офлайн-кодів і час, проведений в офлайні | `GET /api/v1/cash-registers/get-offline-codes-count` та `…/get-offline-time` |
| `get_current_shift` | Відкриту зміну касира з поточним балансом | `GET /api/v1/cashier/shift` |
| `list_shifts` | Зміни касира або зміни каси | `GET /api/v1/shifts` або `GET /api/v1/cash-registers/shifts` |
| `get_shift` | Одну зміну повністю, разом із Z-звітом після закриття | `GET /api/v1/shifts/{id}` |
| `search_receipts` | Чеки за періодом, фіскальним номером, штрихкодом, зміною, касою, торговою точкою | `GET /api/v1/receipts/search` |
| `get_receipt` | Один чек у форматі JSON або як текст для друку | `GET /api/v1/receipts/{id}` або `…/{id}/text` |
| `list_reports` | X- та Z-звіти з підсумками за формами оплати | `GET /api/v1/reports/search` |
| `get_report` | Один звіт у форматі JSON або як текст для друку | `GET /api/v1/reports/{id}` або `…/{id}/text` |
| `get_periodical_report` | Періодичний звіт за вибраний проміжок, текстом | `GET /api/v1/reports/periodical` |
| `search_goods` | Товари з номенклатури Checkbox із цінами та податковими ставками | `GET /api/v1/goods` |
| `list_taxes` | Податкові ставки, налаштовані для організації | `GET /api/v1/cashier/tax` |
| `list_orders` | Замовлення (проєкти чеків, які створила зовнішня система) | `GET /api/v1/orders` |
| `get_order` | Одне замовлення повністю, разом із даними про доставку покупцеві | `GET /api/v1/orders/{id}` |

Інструменти-списки повертають стислі зведення і блок `pagination`. Типовий розмір сторінки — 25, найбільший — 100 (для змін каси — 50, бо це обмеження самого методу API); поле `next_offset` підказує моделі, звідки читати далі.

### Інструменти запису (лише з `CHECKBOX_ALLOW_WRITE=1`)

| Інструмент | Що робить | Запит до API |
| --- | --- | --- |
| `open_shift` | Відкриває зміну на касі, якій належить ключ ліцензії | `POST /api/v1/shifts` |
| `close_shift` | Закриває поточну зміну і формує її Z-звіт | `POST /api/v1/shifts/close` |
| `create_sale_receipt` | Створює і фіскалізує чек продажу | `POST /api/v1/receipts/sell` |
| `create_return_receipt` | Створює і фіскалізує чек повернення | `POST /api/v1/receipts/sell` з ознакою `is_return` у кожному рядку |
| `create_service_receipt` | Службове внесення готівки в касу або службова видача | `POST /api/v1/receipts/service` |
| `send_receipt_email` | Надсилає копію чека електронною поштою | `POST /api/v1/receipts/{id}/email` |
| `send_receipt_sms` | Надсилає копію чека через SMS або Viber (послуга Checkbox з окремою оплатою) | `POST /api/v1/receipts/{id}/sms` |

**Чек — фіскальний документ. Створений чек не можна ні змінити, ні видалити; помилку можна лише компенсувати окремим чеком повернення.** Те саме стосується відкритої чи закритої зміни.

## Модель безпеки

Фіскальні чеки — юридично значущі документи, тому сервер навмисно обережний.

- **Без вашого дозволу — тільки читання.** Без `CHECKBOX_ALLOW_WRITE=1` інструменти запису взагалі не реєструються: модель їх не бачить і викликати не може. Кожен інструмент читання надсилає лише запити `GET`, і це перевіряє окремий тест.
- **Чесні анотації.** Інструменти читання мають `readOnlyHint: true`. Інструменти, що створюють фіскальні записи (`open_shift`, `close_shift` і три інструменти для чеків), мають `destructiveHint: true`: формально вони лише додають дані, але результат не можна скасувати, і саме ця позначка спонукає MCP-клієнт просити у вас підтвердження. Жоден інструмент запису не позначено як ідемпотентний. Чи показувати підтвердження і як саме, вирішує ваш MCP-клієнт; не вимикайте підтвердження кожного виклику для інструментів запису.
- **Сувора перевірка вхідних даних для запису.** Інструменти запису відхиляють невідомі поля, нецілі суми й неправильно записані контакти ще до надсилання. Тож помилка в назві поля, як-от `discount`, не призведе до чека з неправильною сумою.
- **Жодних повторів наосліп.** Сервер сам ніколи не повторює запит на запис. Єдиний виняток — один повтор після відповіді HTTP 401, яку Checkbox повертає, ще не почавши обробляти запит. Якщо час очікування сплив, інструмент повідомляє, що результат невідомий, і пояснює, як його перевірити. Кожна нова зміна й кожен новий чек заздалегідь отримують UUID; другий документ із тим самим ідентифікатором Checkbox відхиляє, тож повтор із цим UUID не створить дубліката.
- **Жодного обходу перевірок самого Checkbox.** `close_shift` не дає змоги вимкнути перевірку того, що зміну закриває та сама програма, яка її відкрила.
- **Облікові дані зберігаються лише у вас.** Сервер читає їх зі змінних середовища, використовує лише для запитів до `CHECKBOX_API_URL` і ніколи не виводить у stdout, stderr чи результати інструментів. Токен доступу зберігається тільки в пам’яті й анулюється, коли MCP-клієнт від’єднується (наскільки це можливо: примусово зупинений процес цього не зробить).
- **Моделі — менше даних.** Інструменти-списки повертають зведення без контактів покупців; податковий номер касира вилучається з усіх результатів. Натомість `get_receipt` і `get_order` повертають повні записи, де можуть бути електронна адреса, телефон і адреса доставки покупця.
- **Жодної телеметрії; чеки й контакти не потрапляють у журнали.** У stderr потрапляють лише повідомлення під час запуску (помилки налаштувань і рядок із режимом роботи) та тип помилки транспорту. Запити й відповіді ніде не записуються.

Двох речей сервер за вас не зробить. По-перше, усе, що повертає інструмент, потрапляє до ШІ-моделі, якою ви користуєтеся, і до її постачальника; зважте, чи прийнятно це для ваших даних. По-друге, назви товарів, коментарі та інший текст із Checkbox модель отримує без змін, і в ньому можуть бути чужі інструкції (prompt injection). Це ще одна причина підтверджувати кожен виклик запису власноруч.

## Як спробувати на тестових даних Checkbox

Нижче — те, що написано в документації Checkbox. Сам проєкт у такий спосіб **ще не перевіряли**.

- Окремої тестової адреси немає. За [вікі](https://wiki.checkbox.ua/uk/api), `https://api.checkbox.ua` — єдина адреса і для тестування, і для фіскальної роботи. Тестовим сеанс робить те, під яким касиром і з якою касою ви входите.
- **Тестовий касир** і **тестова каса** з’являються в особистому кабінеті Checkbox автоматично після реєстрації ([вікі: тестові дані](https://wiki.checkbox.ua/uk/portal/test-data)). Тестові чеки не передаються до ДПС і мають позначку «Тестовий чек». Checkbox обмежує їх кількість: 100 на місяць.
- Пароль тестового касира збігається з його логіном ([вікі: авторизація](https://wiki.checkbox.ua/uk/api/auth)).
- Checkbox застерігає: ніколи не тестуйте на бойовій касі чи бойовому касирі. За некоректні дані, передані до податкової, доведеться давати пояснення, і це може закінчитися штрафом.

Розважливий перший крок: налаштуйте сервер із даними тестового касира, не задавайте `CHECKBOX_ALLOW_WRITE` і викличте `get_cashier_profile`. У відповіді має бути `is_test: true`. Лише після цього вмикайте режим запису — теж із тестовими даними.

## Обмеження

- **Сервер не перевірено зі справжнім API.** Запити звірено з описом OpenAPI, а він описує структуру даних, а не поведінку. Обробку відповідей, тексти помилок і асинхронну зміну статусів реалізовано за документацією.
- **Один касир на один екземпляр сервера** і одна каса для інструментів, яким потрібен ключ ліцензії.
- **Чого немає:** роботи в офлайн-режимі (перехід в офлайн і онлайн, офлайн-чеки), створення X-звітів, чеків передплати й післяплати, обміну валют, інвойсів і роботи з терміналами еквайрингу, редагування товарів, експрес-накладних служб доставки (ЕТТН), вебхуків, розширених звітів, шаблонів чеків.
- **`search_receipts` не фільтрує за статусом і типом**, бо API не має такого параметра; інструмент повертає обидва поля для кожного чека. Якщо не вказати інше, API повертає тільки чеки, створені касиром, під яким виконано вхід.
- **Фіскалізація асинхронна.** Новий чек або зміна повертається зі статусом `CREATED`; модель має сама перевіряти стан через `get_receipt` чи `get_current_shift`. Сервер не чекає.
- **У чеку повернення оплати передаються додатними сумами.** В описі OpenAPI про це прямо не сказано, тож це треба підтвердити на тестовій касі.
- **Для більшості списків немає загальної кількості.** API повідомляє її лише для замовлень, тому сервер може сказати тільки, що далі, можливо, є ще сторінка.
- **Сервер не стежить за лімітами частоти запитів.** За документацією Checkbox, на одній касі можна створювати не більше ніж два чеки за секунду (перевищення блокує касу на 5 секунд), а три запити за секунду на перегляд того самого чека призводять до блокування.
- **Токени.** За документацією Checkbox, касир може мати не більше ніж три чинні токени. Сервер входить один раз після запуску й виходить після від’єднання клієнта, проте це може зачепити касира, який одночасно працює ще десь.
- **Не поєднуйте різні програми в межах однієї зміни.** Checkbox попереджає: якщо зміну відкрито через API, одночасно працювати з нею в Checkbox Kasa чи Manager не можна.
- **Час очікування відповіді фіксований** — 30 секунд на запит.

## Розробка

```bash
npm install
npm run lint          # tsc --noEmit для src/ і tests/
npm test              # збирає dist/ і тести, потім запускає їх через node:test
npm run spec:update   # оновлює знімок OpenAPI з api.checkbox.ua
```

- `src/endpoints.ts` — перелік методів API, які викликає сервер. `tests/spec.test.ts` порівнює його з `spec/checkbox-api.snapshot.json` — скороченою копією офіційного опису OpenAPI (лише параметри, схеми запитів і вимоги до авторизації для цих методів).
- Кожен тест інструмента викликає його через справжній MCP-клієнт і передає кожен записаний запит до `assertMatchesSpec`; ця функція звіряє шлях, параметри, заголовки й тіло запиту зі знімком.
- `tests/e2e.test.ts` запускає зібраний сервер окремим процесом через stdio; замість API працює локальна HTTP-заглушка.
- Перевірити сервер уручну: `npx @modelcontextprotocol/inspector node dist/index.js`.

Сервер використовує офіційний TypeScript SDK ([`@modelcontextprotocol/server`](https://www.npmjs.com/package/@modelcontextprotocol/server)) і `zod`; інших залежностей для роботи він не має.
